Karta + Kueue + DRA

Demo findings, architectural positioning vs Run:ai / KAI / Grove, and what belongs on a Red Hat OpenShift AI roadmap.

Upstream map project: github.com/dsx-ai-factory/workload-map

Roadmap question

Do we still need a Karta-like layer?

If Kueue decides whether a job may run, and DRA gives it a real GPU — do we still need Karta?

Yes — as a translation pattern.

The capability (declarative CRD → scheduling intent) stays valuable. Whether RH AI adopts the Run:ai Karta binary is a separate decision (see later slides).

Ticket · What Karta adds

Semantic CRD normalization

Karta is a declarative meta-layer: JQ / structural maps that teach the platform how to read any compound CRD.

  • The gap: KAI places pods; Grove owns clique topologies. Neither invents a portable schema for arbitrary CRDs.
  • What Karta adds: A Karta CR (structureDefinition + optimizationInstructions) so admins map RayJob, custom trainers, etc. without writing a Go controller per CRD.
  • Fallback idea: If a native integration already exists, use it; otherwise the map bridges the long tail into gang / queue / telemetry intent.

Finding 1

Kueue owns admit vs queue

Admitted

Takes the only example.com/gpu slot.

→quota = 1
dra-job-queued
Pending

Waits until the first releases quota.

  • Proves fair queuing of GPU-shaped jobs — not full device bind.
  • Works without a real GPU DRA driver.

Finding 2

Karta still maps the Job

Not a scheduler. Not a queue. A declarative contract — including DRA paths.

Pod template.spec.template
DRA claims.spec.template.spec.resourceClaims
Suspend / resume.spec.suspend (same field Kueue uses)
  • Demo shows map + Kueue coexisting. Out-of-box Karta→Kueue Workload emission still needs glue / redesign.

Finding 3

DRA is a separate layer

This demo uses

  • ResourceClaimTemplate single-gpu
  • DeviceClass gpu.example.com
  • Container claims: — not nvidia.com/gpu: 1

Full bind needs

  • DRA APIs on the cluster
  • Real device driver + ResourceSlices
  • Honest vendor DeviceClass in production
  • Pending claims at Layer 3 do not invalidate Layer 1 admission.

OpenShift path

Bypassing KAI is viable

Combining Karta (or a Karta-like mapper), Grove, and OpenShift’s native Workload API creates a streamlined AI stack that can eliminate a secondary scheduler binary like KAI.
  • No hard code dependency on KAI — but Run:ai’s product path has a strong operational one (EWI / dromos / PodGroup targets).
  • Demo sibling karta-decoupled-scheduler already runs with default kube-scheduler.
  • RH goal: Run:ai-like CRD onboarding UX on Kueue + DRA + WAS, not KAI.

Capability gap

Fractional GPUs without Run:ai

Run:ai’s strength is dynamic fractioning + VRAM swap. On OpenShift, three native-ish paths:

1. Time-slicing

GPU Operator replicas (e.g. 4). Pods request nvidia.com/gpu: 1 = one slice. No hard VRAM isolation — noisy neighbor risk.

2. MIG

Hardware partitions on A100/H100. Strict isolation closer to Run:ai memory boundaries; profile resets required.

3. Dynamic slicing

Red Hat Dynamic Accelerator Slicer: on-demand slices via scheduling gates — less idle silicon than static replicas.

  • Quota borrow / reclaim ≈ Kueue cohorts + ReclaimWithinCohort. Portal / idle cull ≈ RHOAI dashboard + notebook culler. Multi-cluster ≈ RHACM.

Ticket answers

RH AI roadmap fit

  • Can we use this in RH AI?
    Conceptually yes — zero-code CRD onboarding is real. Prefer aligning with upstream KEP-6012 CompositePodGroup over adopting Run:ai Karta as a product dependency.
  • Hard dependencies on KAI?
    No hard code deps, but gang payloads historically target KAI PodGroups. Decoupling means retargeting the output layer.
  • Works with Kueue?
    Yes with glue — demo coexists (map + queues). Emitting native Kueue Workload objects from arbitrary CRDs is the redesign opportunity.

Recommendation

What Red Hat should do

Option A — Recommended

Native upstream path: KEP-6012 CompositePodGroup + Kueue for compound CRDs. Standardize on Kueue + DRA + WAS.

Option B — Inspired by Karta

Build a Kueue Workload Mapper (JQ-style maps) that emits Kueue Workloads — not KAI PodGroups.

  1. Keep the translation pattern; avoid Run:ai Karta as a hard RH AI binary dependency.
  2. Demo proved: GPU-shaped jobs admit/queue via Kueue + DRA claims; Karta map still useful; full GPU bind needs a driver.
